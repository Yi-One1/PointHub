# ADR-0003：本机导入读取本机客户端登录态（仅 Windows）

- 状态：已采纳
- 日期：2026-11-26
- 相关：`DECISIONS.md` D16；修正 D04 / D13 的适用范围

## 背景

需求 6 要求账号导入同时提供「本机导入」和「浏览器授权」两种方式。
此前的 D04 / D13 明确放弃了读取本机客户端登录态，只做长效令牌导入与官方插件授权。
结果是「本机导入」一项完全缺失。

参考项目 CheckinBox-Tools 的「本机导入」就是从本机客户端的存储里读登录态，
但它没有 LICENSE，不能复制代码，只能借鉴接口与文件格式事实。

## 决策

1. Windows 端提供「本机导入」：扫描并读取本机已登录客户端的登录态，
   转成 `Credential` 后按正常流程验证余额，验证通过才落库。
2. 按平台逐个支持，能力矩阵如实标注：已支持 / 待实现 / 不支持。
3. 只读，不修改客户端文件；读取失败必须给出人话原因，不静默。
4. 安卓端不提供本机导入——客户端不在手机上。

## 理由

- 需求明确要求两种导入方式，缺一不可。
- 「装了客户端就能导入」比让用户手工复制令牌省事，尤其是 Trae / Qoder
  这类凭据形态复杂、还需要设备标识的平台。

## 代价

- 各客户端存储格式与加密方式不同，客户端升级可能导致导入失效，需要持续维护。
- 读取加密存储需要引入 SQLite / 解密相关依赖，会增大 Windows 包体积，
  需要在实现时权衡（优先纯 Rust、按需编译）。
- 与 D05「换机必须重新导入」仍然一致：本机导入只是换了一种取得凭据的方式。

## 边界

- 不复制参考项目源码；只使用公开的文件路径、格式与接口事实。
- 不修改、不备份客户端数据库到仓库；读取产生的临时明文只在内存中存在。
- 读取不到就明确失败，不回退到猜测令牌。

## 何时该重新审视

- 若某平台的登录态无法在不破坏客户端的前提下读取，该平台退回手动令牌，
  并在能力矩阵中如实标注。
